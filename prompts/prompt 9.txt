==================================================
MODULE 9 — FACT VERIFICATION + CLAIM EVALUATION
==================================================

GOAL:

Build the next analysis layer that evaluates extracted claims using the evidence retrieved in MODULE 8.

The system should:

1. Load an extracted claim.
2. Load its retrieved evidence.
3. Evaluate whether the available evidence supports, contradicts, or is insufficient to evaluate the claim.
4. Store a structured verification result.
5. Display the result in the frontend.

IMPORTANT:

This module is about CLAIM EVALUATION.

It is NOT about judging the entire debate yet.

STEP 2 — VERIFICATION RESULT MODEL
==================================================

Create a model for storing the evaluation of a claim.

Suggested model:

ClaimVerification

Fields:

- id
- claim_id
- verdict
- explanation
- evidence_summary
- confidence
- created_at
- updated_at

Adapt names to the existing project conventions.

The verdict must use a controlled set of values.

Recommended:

- supported
- contradicted
- insufficient_evidence

Do NOT use:

- true
- false

The reason is that evidence-based evaluation should communicate what the retrieved evidence indicates without pretending that the system has absolute truth.

Confidence can use:

- low
- medium
- high

OR a numeric value if the existing architecture strongly benefits from it.

Do not overcomplicate this.

STEP 4 — VERIFICATION SERVICE
==================================================

Create a dedicated:

ClaimVerificationService

Responsibilities:

1. Load the claim.
2. Load evidence associated with the claim.
3. Build a structured verification prompt.
4. Send the claim + evidence to the existing LLM provider.
5. Parse the structured response.
6. Validate the response.
7. Persist the verification result.
8. Return the result.

Do NOT make direct Groq SDK calls.

Use the existing provider abstraction.

==================================================
STEP 5 — VERIFICATION PROMPT
==================================================

Create a carefully constrained system prompt for claim evaluation.

The model must:

- evaluate ONLY the provided claim
- use ONLY the provided evidence
- not use outside knowledge
- not invent evidence
- not invent sources
- distinguish supporting evidence from contradictory evidence
- identify insufficient evidence when sources do not adequately establish the claim
- explain its reasoning briefly
- remain neutral
- not evaluate the personality or quality of the agent

The model should return structured JSON.

Example:

{
  "verdict": "supported",
  "confidence": "medium",
  "explanation": "The retrieved sources provide evidence consistent with the claim.",
  "evidence_summary": "Source A reports ..., while Source B ..."
}

The exact schema can be adapted to the project.

==================================================
STEP 6 — IMPORTANT EVIDENCE RULE
==================================================

The LLM MUST NOT create evidence.

The verification service may only reference evidence already stored in the Evidence table.

For every source mentioned in the verification result, there must be a corresponding stored evidence record.

If there is no evidence:

verdict = insufficient_evidence

Do NOT allow the LLM to invent:

- URLs
- article titles
- organizations
- statistics
- quotations
- citations

==================================================
STEP 7 — EVIDENCE SUFFICIENCY
==================================================

Implement sensible handling for claims with:

1. No evidence
2. One evidence result
3. Multiple evidence results
4. Conflicting evidence
5. Irrelevant evidence

Examples:

No evidence:
→ insufficient_evidence

Evidence directly supports the claim:
→ supported

Evidence directly contradicts the claim:
→ contradicted

Evidence is ambiguous or insufficient:
→ insufficient_evidence

Sources disagree:
→ do not force supported/contradicted.
→ use insufficient_evidence when the conflict cannot be resolved from the provided evidence.

Do not pretend certainty where evidence is inconclusive.

STEP 9 — VERIFICATION API
==================================================

Add an authenticated endpoint.

Suggested:

POST

/api/v1/claims/{claim_id}/verify

Requirements:

- JWT authentication
- verify claim exists
- verify the claim belongs to a debate owned by the current user
- load stored evidence
- perform evaluation
- persist result
- return result

IMPORTANT:

This endpoint must NOT automatically perform Tavily retrieval.

Verification should use evidence already retrieved by Module 8.

If no evidence exists, return:

insufficient_evidence

without pretending verification was performed successfully.

You may choose either:

A) return a structured insufficient_evidence result

OR

B) return a clear validation response requiring evidence retrieval first

Prefer A because it keeps the API useful.

STEP 11 — RE-VERIFICATION
==================================================

Allow a claim to be evaluated again after new evidence has been retrieved.

Do not create uncontrolled duplicate verification records.

Choose a clean strategy consistent with the existing architecture:

Option A:
Maintain one current verification result per claim and update it.

Option B:
Maintain verification history and expose the latest result.

Prefer the simpler approach unless the existing architecture already supports history.

If using one current result per claim, enforce uniqueness on claim_id.
