==================================================
MODULE 7 — LIVE DEBATE STREAMING + WEBSOCKETS
==================================================

The purpose of this module is to allow the frontend to observe a running debate in real time.

Current behavior:

POST /api/v1/debates/{debate_id}/start

runs the debate and persists messages.

After this module, the frontend should be able to connect to a WebSocket and receive events while the debate is running.

Conceptually:

Frontend
    ↓
WebSocket
    ↓
FastAPI WebSocket endpoint
    ↓
Debate event manager
    ↓
Debate engine
    ↓
Agent generates response
    ↓
Message persisted
    ↓
Event broadcast
    ↓
Frontend displays response immediately

5. WEBSOCKET ENDPOINT
==================================================

Create:

/ws/debates/{debate_id}

or an equivalent route consistent with the current project.

The WebSocket must:

1. Accept connection.
2. Authenticate user.
3. Verify the debate exists.
4. Verify the authenticated user owns the debate.
5. Register the connection with the debate.
6. Keep the connection alive.
7. Send events.
8. Remove the connection when disconnected.

Unauthorized users must not be able to subscribe to another user's debate.

==================================================
6. WEBSOCKET AUTHENTICATION
==================================================

Reuse the authentication architecture from Module 2.

Do NOT create a second authentication system.

The WebSocket must validate the existing JWT.

Choose a practical approach compatible with the current frontend.

Preferred:

WebSocket query parameter:

/ws/debates/{debate_id}?token=<JWT>

If the existing architecture has a safer compatible mechanism, use it.

Important:

- never log the JWT
- never broadcast the JWT
- never store the JWT in the database
- reject invalid/expired tokens

If authentication fails, close the WebSocket with an appropriate close code.

Document the authentication mechanism.

agent_message

        "agent": {
            "id": "...",
            "name": "Economist",
            "role": "economist"
        },
        "content": "..."
    }
}

IMPORTANT:

The message should be broadcast only after the response has been successfully generated and persisted.

Do not broadcast fake or unpersisted content.

--------------------------------------------------

round_completed

debate_completed

    }
}

--------------------------------------------------
debate_failed
--------------------------------------------------

Include:

- status
- safe error message

Never expose stack traces or API keys.

13. MESSAGE PERSISTENCE ORDER
==================================================

For an agent message:

1. Agent turn starts.
2. Emit agent_turn_started.
3. Generate LLM response.
4. Persist message to PostgreSQL.
5. Commit transaction.
6. Emit agent_message.
7. Emit agent_turn_completed.

This ordering is important.

The frontend should never receive an `agent_message` that does not exist in PostgreSQL.

==================================================
14. ROUND EVENT ORDER
==================================================

Round execution:

1. Create round.
2. Mark round running.
3. Commit.
4. Emit round_started.
5. Execute turns.
6. Mark round completed.
7. Commit.
8. Emit round_completed.

==================================================
15. DEBATE EVENT ORDER
==================================================

When start begins:

1. Verify debate can start.
2. Mark debate running.
3. Commit.
4. Emit debate_started.
5. Run rounds.
6. Mark debate completed.
7. Commit.
8. Emit debate_completed.

If failure:

1. Mark debate failed.
2. Commit.
3. Emit debate_failed.

==================================================
16. RECONNECT BEHAVIOR
==================================================

Implement simple reconnect behavior.

If the browser disconnects:

- remove the socket
- do not stop the debate
- do not modify debate state

If the browser reconnects:

- authenticate again
- verify ownership again
- connect again
- fetch current debate state through normal HTTP

Do NOT attempt to replay the entire missed WebSocket event history.

The frontend should use:

GET /api/v1/debates/{debate_id}

and:

GET /api/v1/debates/{debate_id}/messages

to recover current state.

==================================================
17. WEBSOCKET DOES NOT CONTROL THE DEBATE
==================================================

Closing the WebSocket must NOT:

- stop the debate
- cancel the LLM request
- mark the debate failed
- delete messages

The WebSocket is only an observation channel.

The DebateEngine remains responsible for execution.
