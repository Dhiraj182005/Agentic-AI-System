MODULE 6 — DEBATE ORCHESTRATION + MULTI-AGENT DEBATE ENGINE
==================================================

This module introduces the actual multi-agent debate execution.

The goal is:

Created Debate
      ↓
Load Debate
      ↓
Load Selected Agents
      ↓
Initialize Runtime Agents
      ↓
Round 1
      ↓
Agent Responses
      ↓
Round 2
      ↓
Rebuttals
      ↓
...
      ↓
Final Debate Transcript
      ↓
Debate Completed

- debate orchestration

9. START DEBATE ENDPOINT
==================================================

Create:

POST /api/v1/debates/{debate_id}/start

Require authentication.

Verify the debate belongs to the authenticated user.

Behavior:

1. Load debate.
2. Verify status is `created`.
3. Load selected agents.
4. Initialize runtime agents.
5. Change status to `running`.
6. Execute configured rounds.
7. Persist every agent response.
8. Complete the debate.
9. Return final execution status.

Do NOT allow starting:

- another user's debate
- completed debate
- failed debate unless explicit retry support is implemented
- already running debate

Return appropriate HTTP errors.

==================================================
10. DO NOT RUN DEBATES DURING CREATION

POST /api/v1/debates

must ONLY create the debate.

It must NOT call:

Groq
BaseAgent
DebateEngine

The only endpoint that starts execution in this module is:

POST /api/v1/debates/{debate_id}/start

11. AGENT TURN ORDER
==================================================

Use the order in which agents are associated with the debate.

Example:

1. Economist
2. Lawyer
3. Scientist
4. Ethicist

For every round:

Economist
 ↓
Lawyer
 ↓
Scientist
 ↓
Ethicist

Then next round:

Economist
 ↓
Lawyer
 ↓
Scientist
 ↓
Ethicist

Do NOT randomly reorder agents.

Do NOT dynamically select agents using an LLM.

Do NOT remove agents during the debate.

Keep turn order deterministic.

==================================================
12. ROUND STRUCTURE
==================================================

Implement a simple deterministic structure.

Example for 3 rounds:

ROUND 1
- Each agent gives an opening argument.

ROUND 2
- Each agent gives a rebuttal based on previous arguments.

ROUND 3
- Each agent gives a final position.

Use message_type:

round 1 → opening
round 2 → rebuttal
final round → closing

If total_rounds differs:

- first round = opening
- middle rounds = rebuttal
- final round = closing

Do not create different debate logic for every possible round count.

==================================================
13. AGENT CONTEXT
==================================================

The agent must receive enough context to respond meaningfully.

Round 1 context:

- debate topic
- role identity
- instructions to provide an opening argument

Round 2+ context:

- debate topic
- role identity
- previous relevant debate messages
- instruction to respond/rebut

Final round:

- debate topic
- previous messages
- instruction to provide final position

Use a controlled context format.

Do NOT dump unlimited conversation history into every request.

For now, use the existing persisted transcript as the source of context.

If context becomes too large, implement a reasonable limit.

Do not build sophisticated summarization yet.

15. IMPORTANT: NO FAKE REBUTTALS
==================================================

A rebuttal must actually receive previous arguments as context.

Do NOT generate generic:

"Some people believe X..."

without providing the previous transcript.

The sequence must be:

Agent A response
    ↓
persist
    ↓
Agent B receives Agent A response
    ↓
Agent B response
    ↓
persist
    ↓
Agent C receives A + B
    ↓
Agent C response

etc.

==================================================
16. TRANSCRIPT PERSISTENCE
==================================================

Every generated message must be persisted immediately after successful generation.

Do not wait until the entire debate completes before saving all messages.

Example:

Agent 1 generates
 ↓
save message

Agent 2 generates
 ↓
save message

Agent 3 generates
 ↓
save message

This prevents losing the entire transcript if a later request fails.

==================================================
18. CONCURRENCY
==================================================

Do NOT execute agents in parallel in this module.

Agents must execute sequentially.

Reason:

Later agents need previous agents' responses as context.

Correct:

Agent A
 ↓
Agent B
 ↓
Agent C

Incorrect:

Agent A ─┐
Agent B ─┼─ parallel
Agent C ─┘

==================================================
20. FAILURE HANDLING
==================================================

If one agent fails:

1. Log the failure safely.
2. Mark the current round as failed.
3. Mark the debate as failed.
4. Do not mark debate completed.
5. Preserve all previously generated messages.

Do not delete the transcript.

Do not expose internal exceptions to the frontend.

Return a controlled error response.

Do NOT automatically retry multiple times in this module unless the existing provider layer already provides safe retry handling.

Keep retry behavior simple.

==================================================
21. IDEMPOTENCY / DUPLICATE START
==================================================

POST /start

from starting the same debate twice.

running

return an appropriate conflict response.

If status is:

completed

return an appropriate conflict response.

Do not create duplicate rounds.

22. TRANSACTION BOUNDARIES
==================================================

Do NOT hold one giant database transaction around the entire debate.

That would be dangerous for long-running LLM calls.

Instead:

- update status
- commit
- generate response
- save message
- commit
- continue

Keep database transactions short.
