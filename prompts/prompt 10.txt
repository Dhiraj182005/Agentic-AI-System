==================================================
MODULE 10 — FALLACY DETECTION + DEBATE QUALITY ANALYSIS
==================================================

GOAL:

Add an AI-powered analysis layer that detects logical/rhetorical fallacies in debate messages and evaluates the quality of individual arguments.

The system should:

1. Analyze persisted debate messages.
2. Detect possible fallacies.
3. Identify the fallacy type.
4. Provide a concise explanation.
5. Assign severity/confidence.
6. Evaluate argument quality.
7. Store the results.
8. Display the results in the frontend.

This module analyzes the QUALITY OF ARGUMENTS.

It does NOT decide the overall winner of the debate.

==================================================
STEP 3 — FALLACY TYPES
==================================================

Use a controlled vocabulary.

Start with a practical set:

- ad_hominem
- straw_man
- false_dilemma
- slippery_slope
- appeal_to_authority
- appeal_to_emotion
- hasty_generalization
- circular_reasoning
- red_herring
- false_cause
- bandwagon
- loaded_question
- no_fallacy

You may add a small number of commonly recognized fallacies if the existing architecture benefits from them.

Do NOT create dozens of obscure categories.

The model should prefer:

no_fallacy

when evidence for a fallacy is weak.

==================================================
STEP 4 — FALLACY SEVERITY
==================================================

Use:

- low
- medium
- high

Severity describes the impact of the detected fallacy on the argument.

It does NOT mean the argument is false.

Example:

An argument can contain a low-severity rhetorical issue while still containing a valid factual claim.

==================================================
STEP 5 — FALLACY DETECTION SERVICE
==================================================

Create:

FallacyDetectionService

It should:

1. Load a debate message.
2. Optionally load limited relevant conversation context.
3. Analyze the argument using the existing LLM provider.
4. Identify whether a fallacy exists.
5. Identify the fallacy type.
6. Assign severity.
7. Assign confidence.
8. Provide a concise explanation.
9. Identify the relevant text span.
10. Persist the result only when a real fallacy is detected.

IMPORTANT:

Do NOT directly call Groq.

Use the existing LLM provider abstraction.

==================================================
STEP 6 — FALLACY PROMPT
==================================================

Create a strict analysis prompt.

The model must:

- analyze the argument objectively
- distinguish rhetorical disagreement from logical fallacy
- not label disagreement as a fallacy
- not assume an argument is fallacious simply because it is controversial
- identify the exact reasoning pattern
- provide concise reasoning
- avoid political or ideological bias
- avoid judging the speaker
- avoid judging whether the claim itself is factually true
- use only the supplied text/context

The model should return structured JSON.

Example:

{
  "fallacy_type": "straw_man",
  "severity": "medium",
  "confidence": 0.87,
  "explanation": "The response reframes the opposing position into a stronger claim that was not actually made.",
  "evidence_span": "..."
}

If no fallacy is detected:

{
  "fallacy_type": "no_fallacy",
  "severity": "low",
  "confidence": 0.91,
  "explanation": "The argument does not show a clear recognizable logical fallacy.",
  "evidence_span": null
}

==================================================
STEP 7 — STRUCTURED OUTPUT VALIDATION
==================================================

Use Pydantic validation.

Validate:

- fallacy_type
- severity
- confidence
- explanation
- evidence_span

Rules:

confidence must be between 0 and 1.

Reject:

- invalid fallacy types
- invalid severity
- missing explanation
- invalid confidence
- malformed JSON

Handle:

- normal JSON
- markdown code fences
- malformed JSON

Do not persist invalid results.

==================================================
STEP 8 — DO NOT OVER-DETECT FALLACIES
==================================================

This is extremely important.

The system should prefer:

"No fallacy detected"

over falsely labeling an argument.

Examples:

Disagreement ≠ ad hominem

Strong claim ≠ straw man

Prediction ≠ slippery slope

Emotional language ≠ appeal to emotion automatically

Mentioning an expert ≠ appeal to authority automatically

Correlation ≠ automatically false cause

The detection explanation must justify why the pattern qualifies as a fallacy.

STEP 14 — ARGUMENT QUALITY EVALUATION
==================================================

- logical reasoning
- evidence usage
- relevance to topic
- effectiveness of argument

IMPORTANT:

Do NOT interpret the score as truth.

For example:

A score of 9 does NOT mean the argument is factually true.

It means the argument is strong according to the defined quality dimensions.

==================================================
STEP 15 — EVALUATION PROMPT
==================================================

Use the existing LLM provider.

The prompt should require structured JSON:

{
  "logical_soundness": 8,
  "evidence_score": 7,
  "relevance_score": 9,
  "effectiveness_score": 8,
  "overall_score": 8.0,
  "explanation": "..."
}

Scoring rules:

0–2 = very weak
3–4 = weak
5–6 = moderate
7–8 = strong
9–10 = excellent

The explanation must be concise.

Do not expose chain-of-thought.

Only store a short justification.

==================================================
STEP 16 — EVIDENCE-AWARE EVALUATION
==================================================

- retrieved evidence
- verification results

the evaluator may use that information as supporting context.

However:

Do NOT replace the existing verification result.

Do NOT independently invent factual verification.

The evaluation should distinguish:

argument quality

from

claim truth.
